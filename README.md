# Fisio Invasiva — migración en desarrollo

**No publicar todavía.** Esta versión requiere ejecutar y revisar la importación completa, comprobar las rutas e imágenes y validar el formulario y la publicación desde Payload. El XML de WordPress no es un respaldo completo.

## Requisitos y configuración

Docker Compose en el servidor y Nginx externo con HTTPS ya instalado. Copia `.env.example` a `.env`; establece una contraseña de PostgreSQL fuerte y alfanumérica y un `PAYLOAD_SECRET` aleatorio largo. Configura SMTP y `CONTACT_FROM` para que el formulario envíe a `CONTACT_TO` (la exportación indica contacto@fisioinvasiva.cl). No subas `.env` ni la exportación a Git.

Ejecuta `docker compose up -d --build`. Solo la app expone el puerto 3000 en 127.0.0.1; PostgreSQL permanece dentro de Docker. En una prueba, usa un hostname privado con autenticación, sin afectar al WordPress activo. El ejemplo `nginx.example.conf` muestra el bloque que se debe adaptar al servidor HTTPS existente. Protege el acceso a la instancia de prueba y crea el primer usuario en `/admin` antes de hacerla accesible; conserva sus credenciales de forma segura.

La migración inicial de PostgreSQL está en `src/migrations` y Payload la ejecuta al inicializarse en producción. Conserva los volúmenes `pgdata` y `media` entre reconstrucciones del contenedor.

## Prueba en dev.fisioinvasiva.cl

Apunta el subdominio al servidor y crea un bloque HTTPS separado en el Nginx existente con `server_name dev.fisioinvasiva.cl`. Usa `nginx.dev.conf` como archivo de sitio: incluye el proxy a `127.0.0.1:3000`, los certificados, la autenticación HTTP y `X-Robots-Tag: noindex, nofollow`. Crea `/etc/nginx/.htpasswd-fisio-dev` antes de activar el archivo, verifica que el certificado del servidor cubra `dev.fisioinvasiva.cl` y activa Authenticated Origin Pulls en Cloudflare. Deja el bloque de `fisioinvasiva.cl` apuntando a WordPress.

En el directorio del repositorio del servidor, crea `.env` desde `.env.example`, configura al menos `POSTGRES_PASSWORD` y `PAYLOAD_SECRET`, y ejecuta `docker compose up -d --build`. Compose genera `DATABASE_URL` con el host interno `db`; no tienes que definirlo en `.env` para el despliegue. Abre `https://dev.fisioinvasiva.cl/admin` para crear el primer usuario de Payload. El autor de WordPress se conserva como texto en los artículos importados; su cuenta para publicar en Payload se crea por separado en `/admin`.

## Importación

Copia la exportación WXR dentro del contenedor con `docker compose cp /ruta/exportacion.xml app:/tmp/wordpress.xml` y ejecuta `docker compose exec app npm run import:wordpress -- /tmp/wordpress.xml --inventory` para inventariar. Ejecuta luego el mismo comando sin `--inventory` para importar. El script actualiza por ID de WordPress y genera `/app/informe-importacion.md` solo al terminar correctamente; cópialo fuera con `docker compose cp app:/app/informe-importacion.md ./informe-importacion.md` antes de reconstruir el contenedor. Cada sincronización sobrescribe los campos importados salvo el contenido del editor visual de las entradas que ya lo tienen publicado: evita editar los demás campos en Payload hasta después de la última sincronización.

WordPress debe seguir en línea durante la importación porque el script descarga de allí las imágenes públicas utilizadas. El importador comprueba que cada archivo esté en el volumen `media`, repara archivos perdidos al repetirlo y deja el HTML público con rutas locales. `originalUrl` en Payload conserva el origen solo como referencia. Comprueba el resultado con `docker compose exec db psql -U fisio -d fisio -c "SELECT kind, visibility, count(*) FROM content GROUP BY kind, visibility ORDER BY kind, visibility;"` y `docker compose exec db psql -U fisio -d fisio -c "SELECT count(*) FROM content WHERE visibility='publish' AND html LIKE '%fisioinvasiva.cl/wp-content/uploads/%';"`; la segunda consulta debe devolver cero. Revisa `/tratamientos/`, `/blog/` y cada artículo en el subdominio. Las rutas de los artículos se importan desde sus URLs originales. Los enlaces absolutos dentro del HTML pueden seguir llevando al WordPress principal durante la prueba; el sitemap actual también usa el dominio principal.

La exportación encontrada contiene 12 entradas públicas, 6 páginas públicas, 1 privada y 105 adjuntos. Para actualizar una instalación ya importada, ejecuta `git pull`, `docker compose up -d --build`, copia otra vez el XML al contenedor y repite `docker compose exec app npm run import:wordpress -- /tmp/wordpress.xml`. Este paso reconstruye las columnas, listas, imágenes y videos de los tratamientos a partir de Elementor y descarga los medios necesarios; actualiza los artículos existentes por ID, sin duplicarlos. El carrusel de imágenes de Elementor se adapta a una galería. Las categorías y etiquetas importadas se pueden filtrar en `/tratamientos/`; las rutas antiguas `/tratamientos/<categoria>/` y `/tag/<etiqueta>/` redirigen con 301. Revisa el informe: shortcodes, formatos de SEO y medios no públicos pueden requerir intervención manual. La página de inicio y las páginas `/nosotros/`, `/testimonios/` y `/contacto/` usan plantillas en código; sus copias importadas permanecen en Payload para consulta, pero editar su contenido visual no cambia estas plantillas.

### Editor visual de Payload

Los tratamientos tienen **Secciones del tratamiento**: cada fila contiene una columna izquierda y una derecha, en el orden de la página. Cada columna permite editar texto, imágenes, un video de YouTube y una galería. Para artículos sin esa estructura está **Contenido del artículo**. La importación nueva prepara las secciones automáticamente. En una instalación ya importada, ejecuta `docker compose exec app npm run backfill:visual` después de reconstruir la app; el comando se puede repetir y prepara las secciones aunque la conversión anterior ya haya rellenado el editor plano. Por seguridad, omite las entradas que ya tengan activada **Publicar contenido editable** para no reemplazar cambios del autor.

Abre un tratamiento en `/admin`, edita una sección y guarda. Los campos de Payload muestran la estructura y el orden; **Vista previa** muestra la estética real de la página. Requiere iniciar sesión en Payload y no altera la página pública. Cuando estés conforme, activa **Publicar contenido editable** y guarda. Hasta entonces la web sigue mostrando el HTML original. Este HTML permanece guardado como respaldo. Una nueva importación conserva las secciones de las entradas que ya tengan activada la publicación editable. Las páginas `/nosotros/`, `/testimonios/` y `/contacto/` siguen usando sus plantillas en código.

## Antes de cambiar el dominio

1. Respalda base de datos y archivos completos de WordPress; conserva su configuración Nginx y confirma cómo restaurarlos. Respalda también los volúmenes de PostgreSQL y media de la prueba.
2. En WordPress congela los cambios editoriales; exporta otra vez e importa la última copia. Revisa el informe y compara totales por estado, contenido, imágenes y URLs. Valida en privado las páginas sensibles. El script no elimina contenido que haya desaparecido de la exportación: compáralo y resuelve diferencias manualmente.
3. Verifica sitemap, 301 necesarios, rutas, formulario con un envío real, enlace y medición de AgendaPro, y la publicación desde `/admin`. La configuración de medición antigua requiere inspección adicional. No cambies el tráfico si hay fallos o referencias antiguas sin resolver.
4. Apunta el Nginx HTTPS existente a `127.0.0.1:3000`, comprueba las funciones anteriores en producción y supervisa errores. Si falla una función crítica, restaura la configuración Nginx anterior y vuelve a iniciar WordPress con su base y archivos intactos.

## Desarrollo local

Si ejecutas la app fuera de Docker con `npm run dev`, configura `DATABASE_URL` hacia una instancia de PostgreSQL accesible desde tu PC y `PAYLOAD_SECRET` en `.env`. Para desplegar con Compose, basta con `POSTGRES_PASSWORD` y `PAYLOAD_SECRET`. `npm run typecheck` comprueba tipos y `npm run build` compila producción.

La opción anterior con [Google Business Profile API](https://developers.google.com/my-business/content/pricing) sigue disponible solo si Google aprueba tu proyecto. En ese caso, deja `REVYS_WIDGET_ID` vacío y sigue estos pasos:

1. Con la cuenta propietaria o gestora de la ficha, crea un proyecto en Google Cloud y [solicita acceso básico a las Business Profile APIs](https://developers.google.com/my-business/content/prereqs). Espera la aprobación. Después habilita **Google My Business API**, **My Business Account Management API** y **My Business Business Information API**. No habilites Places API para este carrusel.
2. Configura la pantalla de consentimiento OAuth y crea un cliente OAuth 2.0 de tipo **Aplicación web**. Autoriza `https://developers.google.com/oauthplayground` como URI de redirección. En [OAuth Playground](https://developers.google.com/oauthplayground), abre la configuración, activa *Use your own OAuth credentials*, ingresa el ID y secreto del cliente, solicita el alcance `https://www.googleapis.com/auth/business.manage`, autoriza con la cuenta que gestiona la ficha e intercambia el código. Guarda el **refresh token** en un lugar seguro. [Guía oficial de OAuth](https://developers.google.com/my-business/content/basic-setup).
3. En `.env` del servidor configura `GOOGLE_BUSINESS_CLIENT_ID`, `GOOGLE_BUSINESS_CLIENT_SECRET` y `GOOGLE_BUSINESS_REFRESH_TOKEN`. No pegues esos valores en el chat ni los subas a Git. Ejecuta `docker compose up -d --build` y luego `docker compose exec app npm run google:locations`. El comando muestra los nombres de las fichas accesibles y el valor `GOOGLE_BUSINESS_LOCATION=accounts/ID/locations/ID`. Copia el correspondiente a Fisio Invasiva en `.env` y ejecuta `docker compose up -d --force-recreate app`.
4. Abre `https://dev.fisioinvasiva.cl/api/google-reviews` tras autenticarte en el subdominio. Debe devolver `"status":"ok"`, el total y las reseñas. Revisa también el carrusel en la landing y en `/testimonios/`. Si devuelve `"unavailable"`, consulta `docker compose logs --tail=80 app`; si devuelve `"unconfigured"`, falta alguna variable.

Si la pantalla OAuth externa sigue en estado *Testing*, Google puede hacer caducar el refresh token a los siete días; [configura el proyecto para producción](https://developers.google.com/identity/protocols/oauth2) antes de depender de la sincronización continua. La API de Perfil de Empresa requiere aprobación y tiene cuotas; si Google rechaza el acceso, usa Revys Free. No se almacenan reseñas en PostgreSQL ni se llama a una API de Google Maps con cobro por consulta.
